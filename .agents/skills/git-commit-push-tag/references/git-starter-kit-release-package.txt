EXTENSION DE RELEASE PROPRE À GIT-STARTER-KIT

Cette extension s'applique lorsque le remote `origin` est exactement
`https://github.com/asphyx0r/git-starter-kit.git`. Les règles de création et
de contrôle de la GitHub Release s'appliquent uniquement lorsque
`CREATE_GITHUB_RELEASE=true`.

PRÉPARATION DU MANIFESTE DE RELEASE

- Après la finalisation du changelog au point 29 et avant toute prévalidation
  distante, exige que `tools/starter-kit-manifest.py` et
  `starter-kit-manifest.json` soient suivis et entièrement lisibles.
- Exécute d'abord, sans écriture :
  `python tools/starter-kit-manifest.py --dry-run prepare --release-ref <tag>`.
- Si le plan est valide, exécute exactement :
  `python tools/starter-kit-manifest.py prepare --release-ref <tag>`.
- Exige que seul `starter-kit-manifest.json` ait été créé ou modifié par cette
  commande. Le manifeste doit identifier le tag exact dans `current`, conserver
  une URL `/releases/tag/<tag>` et inventorier le core avec ses empreintes et
  stratégies.
- Valide le résultat avec :
  `python tools/starter-kit-manifest.py check --expected-ref <tag> --treeish HEAD`.
- Crée un commit distinct de préparation du manifeste en répétant intégralement
  les contrôles et le contrat de commit des points 18 à 28. Ne mélange aucun
  autre changement à ce commit.
- Après le commit, répète le contrôle `check` contre `HEAD`. Tout échec ou toute
  modification supplémentaire bloque la prévalidation distante, le tag et la
  release.
- Exécute ensuite la section « PRÉPARATION DES ARTEFACTS D'IDENTIFICATION DE
  RELEASE » du workflow principal. Ainsi, `manifest.json` et `SHA256SUMS`
  inventorieront le `starter-kit-manifest.json` final destiné au même tag.

PRÉCONDITION DU WORKFLOW DE RELEASE

- Vérifie que `.github/workflows/release-package.yml` :
  - est suivi par Git et entièrement lisible ;
  - porte exactement le nom `Release package` ;
  - écoute l'événement `release` avec le type `published` ;
  - délègue à l'outil suivi du repository la validation de la provenance
    publique enregistrée dans `_agent-rules-source.json` ;
  - n'exige aucun token GitHub App pour accéder au repository source
    public `agent-coding-rules` ;
  - construit et téléverse le package complet et l'upgrade toolkit dans
    un job de packaging ;
  - contient un job de promotion dépendant du packaging, exécuté
    uniquement pour une prerelease issue de l'événement `release`.
  - limite les jobs de package et de promotion au repository exact
    `asphyx0r/git-starter-kit`.
- Si le workflow est absent, illisible ou non conforme, applique les mêmes
  règles d'arrêt que lorsqu'aucun template de release n'est accessible.
- Vérifie aussi que `.github/workflows/agent-rules-update.yml` :
  - est suivi par Git et entièrement lisible ;
  - porte exactement le nom `Agent rules update` ;
  - écoute l'événement `release` avec le type `published` ;
  - exécute son job lors d'une release même si
    `AGENT_RULES_SYNC_ENABLED=false`.
- Vérifie enfin que `.github/workflows/repository-audit.yml` :
  - est suivi par Git et entièrement lisible ;
  - porte exactement le nom `Repository audit` ;
  - écoute l'événement `release` avec le type `published` ;
  - audite la plage complète depuis le tag stable précédent ;
  - publie le job agrégateur `Repository audit`, qui réussit uniquement si
    tous ses jobs enfants réussissent.
- Si l'un de ces deux workflows est absent, illisible ou non conforme,
  applique les mêmes règles d'arrêt.

CRÉATION DE LA PRERELEASE

- Au point 40 du workflow principal, crée la GitHub Release pour le tag
  exact comme prerelease avec
  `--verify-tag --prerelease --latest=false`.
- Enregistre immédiatement son horodatage `publishedAt`.
- Vérifie qu'elle cible le tag exact, qu'elle n'est pas un draft, qu'elle
  est encore une prerelease et que son corps correspond exactement aux
  Release Notes rendues.

CONTRÔLE CI OBLIGATOIRE

- Résous l'identifiant de chacun des trois workflows actifs
  `.github/workflows/agent-rules-update.yml`,
  `.github/workflows/repository-audit.yml` et
  `.github/workflows/release-package.yml`, puis le commit déréférencé du tag.
- Pour chacun des trois workflows, recherche toutes les cinq secondes, pendant
  dix minutes au maximum, le run unique qui respecte simultanément ces
  conditions :
  - le nom et l'identifiant correspondent exactement au workflow résolu ;
  - `event` vaut exactement `release` ;
  - `headBranch` vaut exactement le tag publié ;
  - `headSha` vaut exactement le commit déréférencé du tag ;
  - `createdAt` est supérieur ou égal au `publishedAt` enregistré.
- Si un run unique manque dans le délai imparti, ne modifie pas l'état courant
  de la release, fixe `RELEASE_STATUS=incomplete`, rapporte le workflow et les
  critères non satisfaits, puis arrête le workflow.
- Attends chacun des trois runs identifiés jusqu'à son état terminal avec
  `gh run watch <run-id> --exit-status`. Ne déclenche aucun autre run et ne
  relance pas automatiquement un run identifié.
- Si un run échoue, est annulé, expire ou ne termine pas normalement :
  - collecte son état et les logs des étapes en échec avec des commandes
    en lecture seule ;
  - ne modifie pas la release ni ses éventuels assets ;
  - fixe `RELEASE_STATUS=incomplete` ;
  - rapporte le workflow, l'URL et la conclusion exactes ;
  - arrête le workflow sans déclarer la release terminée.
- Seule une demande utilisateur explicite peut autoriser
  `gh run rerun <run-id> --failed`. Après cette relance, contrôle le même
  run `event=release` et son nouvel attempt. Un run `workflow_dispatch`
  ne peut jamais remplacer ou valider le run automatique obligatoire.
- Après le succès des trois runs, relis leurs métadonnées et exige pour chacun :
  - `status=completed` ;
  - `conclusion=success` ;
  - l'identité exacte du workflow, de l'événement, du tag et du commit.
- Pour `Repository audit`, exige aussi la réussite de tous les jobs enfants et
  du job agrégateur `Repository audit`.
- Vérifie ensuite que la GitHub Release :
  - cible toujours le tag exact et conserve les Release Notes rendues ;
  - n'est ni un draft ni une prerelease ;
  - est marquée comme dernière release ;
  - contient exactement deux assets nommés
    `git-starter-kit-<tag>-with-agent-rules.zip` et
    `git-starter-kit-<tag>-upgrade-toolkit.zip`.
- Télécharge ces deux assets dans un répertoire temporaire hors du working
  tree et vérifie que le SHA-256 de chacun correspond au digest publié par
  GitHub.
- Vérifie le package complet :
  - il contient `AGENTS.md`, `CODING_RULES.md`, `COMMIT_RULES.md`,
    `DOCUMENTATION_RULES.md`, `LANGUAGE_RULES.md`, `RELEASE_RULES.md` et
    `_agent-rules-source.json` ;
  - son manifeste contient le tag et le commit exacts du starter kit,
    `requestedRef=latest`, ainsi qu'un tag SemVer et un commit résolus pour
    `agent-coding-rules` ;
  - `starter-kit-manifest.json` conserve `source`, identifie le tag exact dans
    `current` et utilise l'URL exacte de la release ;
  - `_starter-kit-files.json` utilise le schéma 3 et classe
    `starter-kit-manifest.json` avec la stratégie `starter-kit-state` ;
  - il ne contient aucun fichier réservé au repository source, tel que le
    workflow, les builders, leurs tests ou leur documentation opérateur.
- Vérifie que l'upgrade toolkit contient exactement `README.md`,
  `starter-kit-upgrade.py` et
  `packages/git-starter-kit-<tag>-with-agent-rules.zip`, puis que le
  SHA-256 du package imbriqué est identique à celui du package complet
  publié séparément.
- Supprime uniquement le répertoire temporaire de vérification après avoir
  confirmé qu'il reste dans la racine temporaire attendue.
- Fixe `RELEASE_STATUS=complete` uniquement après la réussite de tous ces
  contrôles. Aucun asset valide ni run manuel ne suffit séparément.
