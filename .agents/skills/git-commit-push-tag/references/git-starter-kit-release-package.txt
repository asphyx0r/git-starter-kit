EXTENSION DE RELEASE PROPRE À GIT-STARTER-KIT

Cette extension s'applique lorsque le remote `origin` est exactement
`https://github.com/asphyx0r/git-starter-kit.git`. Les règles de création et
de contrôle de la GitHub Release s'appliquent uniquement lorsque
`CREATE_GITHUB_RELEASE=true`.

PILOTE DE VALIDATION ET DE SUIVI

- Applique cette section pendant une exécution explicitement autorisée du
  workflow sur ce remote exact. Une analyse du bump seule n'autorise aucune
  installation, écriture, relance, opération Git ou publication. Les règles
  d'arrêt et d'autorisation du workflow principal restent obligatoires.
- La source, les raisons et les limites de ce pilote sont documentées dans
  `docs/release-package.md`, section « Validation evidence and optimization
  pilot ». Ce pilote ne change aucun outil, profil, hook, timeout ni contrôle
  obligatoire du workflow principal.

Registre temporaire des validations

- Pour chaque validation, conserve dans un registre temporaire hors du working
  tree : commande exacte, périmètre, SHA, empreintes des fichiers concernés
  incluant les modifications non commitées, plateforme, versions réellement
  utilisées, empreintes des verrous et configurations, début, fin, code de
  sortie, résultat et référence du journal complet. Pour une CI, ajoute
  repository, identité du workflow, événement, refs attendues et borne
  `created-after`. Une commande en cours n'a pas de résultat final.
- Distingue audit complet, contrôle ciblé, nouvelle tentative, CI et
  vérification des assets. Un audit complet en échec reste en échec : une
  reprise ciblée réussie ne permet jamais de le déclarer réussi. Diagnostique
  l'échec, respecte les autorisations de relance du workflow principal, puis
  exige un audit complet réussi avant les opérations qui en dépendent.

Précontrôles locaux avant les suites longues

- Avant le premier pre-push long, vérifie et prépare une fois l'environnement
  verrouillé nécessaire, dans le périmètre autorisé. Utilise les versions de
  `tools/quality/versions.json`, les verrous Python/npm et les outils externes
  dont l'intégrité a été vérifiée. Les installations Python utilisent
  `--require-hashes` et npm utilise `ci --ignore-scripts`. Les audits
  n'installent aucune dépendance eux-mêmes.
- Les cibles CI restent Python 3.11 sur Linux, Python 3.14 sur Windows et la
  version Node.js déclarée par `policy.nodeCiVersion`. Documente toute différence
  locale ; une analyse Mypy pour deux plateformes ne prouve pas l'exécution des
  tests sur ces deux systèmes.
- Exécute, depuis la racine, les commandes suivantes séparément et dans cet
  ordre, avec les exécutables de l'environnement préparé et les caches Ruff,
  Mypy et npm dirigés vers le répertoire temporaire de la tâche :
  `python -B tools/quality/check-versions.py --runtime` ;
  `npm audit --audit-level=high --include=dev --prefix tools/quality` ;
  `bash tools/repository-audit.sh fast` ;
  `mypy --config-file tools/quality/pyproject.toml --platform linux` ;
  `mypy --config-file tools/quality/pyproject.toml --platform win32`.
- Tout échec bloque la suite dépendante. Après diagnostic et autorisation de
  reprise, requalifie les entrées ou l'environnement modifiés avant de lancer
  une suite longue. Ces précontrôles s'ajoutent aux gates existantes ; ils ne
  remplacent ni l'audit complet ni les tests du pre-push.

Réutilisation limitée des preuves complémentaires

- Réutilise uniquement une lecture ou un diagnostic complémentaire dont la
  commande, le périmètre, le SHA, les empreintes des entrées et l'environnement
  sont identiques. Si un de ces éléments change, la preuve concernée expire.
  Une donnée externe mutable, notamment les avis de sécurité npm, exige une
  nouvelle vérification au point où elle est requise.
- Exécute toujours les contrôles obligatoires à leur point prévu : fichier
  exact du commit, index, objets poussés, head de PR, commit fusionné, audit
  complet, prévalidation distante, branche/tag et assets téléchargés. Un même
  SHA ne dispense d'aucun de ces contrôles. Conserve la sélection des familles
  par les hooks, la suite complète pour une nouvelle branche, les timeouts et
  les critères CI existants. Ne crée aucun cache persistant de validation.

Un propriétaire et un suivi par exécution

- Pour chaque processus local, conserve un propriétaire, son identifiant de
  session/processus et son journal. Reprends ce processus par son identifiant
  plutôt que de lancer une seconde commande pour obtenir son état.
- Pour les gates qui prescrivent `tools/verify-repository-audit-runs.py`,
  conserve une seule instance pour le tuple exact repository, workflow,
  événement, SHA, refs et `created-after`, avec `--poll-seconds 5`. Pour les
  autres gates de release, conserve la découverte du run puis l'unique
  `gh run watch <run-id> --exit-status` prescrits par le workflow principal.
  Reprends le handle du mécanisme prescrit, sans en substituer un autre.
  Conserve tous les délais, critères de sélection et états bloquants. N'ajoute
  pas de boucle concurrente `gh run list` ou `gh run view` pour surveiller une
  gate déjà suivie. Les lectures de diagnostic après un échec restent
  possibles ; aucun autre run vert ne remplace le run requis.
- Lors d'un progrès nouveau, d'un échec ou de la fin, affiche un extrait limité
  par défaut à 30 lignes et 4 000 caractères. Conserve le journal complet et
  la dernière plage lue ; une investigation peut lire une autre plage motivée.
  Ne répète pas un extrait inchangé.
- À la reprise, consulte un état compact : objectif, autorisations, branche et
  SHA, preuves encore valides, échecs non résolus, processus/vérificateurs en
  cours, dernière plage lue et inventaire des artefacts temporaires. Confirme
  leur état avant toute relance. En fin de tâche, supprime uniquement ses
  artefacts temporaires et vérifie leur absence ; préserve ceux préexistants.

PRÉPARATION DU MANIFESTE DE RELEASE

- Après la finalisation du changelog au point 29 et avant toute prévalidation
  distante, exige que `tools/starter-kit-manifest.py` et
  `starter-kit-manifest.json` soient suivis et entièrement lisibles.
- Exécute d'abord, sans écriture :
  `python tools/starter-kit-manifest.py --dry-run prepare --release-ref <tag>`.
- Si le plan est valide, exécute exactement :
  `python tools/starter-kit-manifest.py prepare --release-ref <tag>`.
- Exige que seul `starter-kit-manifest.json` ait été créé ou modifié par cette
  commande. Le manifeste doit identifier le tag exact dans `current`, conserver
  une URL `/releases/tag/<tag>` et inventorier le core avec ses empreintes et
  stratégies.
- Valide le résultat avec :
  `python tools/starter-kit-manifest.py check --expected-ref <tag> --treeish HEAD`.
- Crée un commit distinct de préparation du manifeste en répétant intégralement
  les contrôles et le contrat de commit des points 18 à 28. Ne mélange aucun
  autre changement à ce commit.
- Après le commit et après son intégration contrôlée dans la cible selon le
  point 28, répète le contrôle `check` contre le véritable `HEAD` fusionné.
  Tout échec ou toute
  modification supplémentaire bloque la prévalidation distante, le tag et la
  release.
- Exécute ensuite la section « PRÉPARATION DES ARTEFACTS D'IDENTIFICATION DE
  RELEASE » du workflow principal. Ainsi, `manifest.json` et `SHA256SUMS`
  inventorieront le `starter-kit-manifest.json` final destiné au même tag.

PRÉCONDITION DU WORKFLOW DE RELEASE

- Vérifie que `.github/workflows/release-package.yml` :
  - est suivi par Git et entièrement lisible ;
  - porte exactement le nom `Release package` ;
  - écoute l'événement `release` avec le type `published` ;
  - délègue à l'outil suivi du repository la validation de la provenance
    publique enregistrée dans `_agent-rules-source.json` ;
  - n'exige aucun token GitHub App pour accéder au repository source
    public `agent-coding-rules` ;
  - construit le package complet et l'upgrade toolkit dans
    un job `build` limité à `contents: read` ;
  - scelle un transfert contenant exactement trois fichiers réguliers : les
    deux ZIP nommés pour le tag et `SHA256SUMS`, avec les empreintes des ZIP
    transmises comme sorties du job de build ;
  - contient un job `publish` dépendant de `build`, sous l'environnement
    `release`, seul détenteur de `contents: write`, sans checkout ni exécution
    de code téléchargé ;
  - vérifie le jeu exact de fichiers, les empreintes scellées et `SHA256SUMS`
    avant de téléverser les trois chemins explicites, sans `--clobber` ;
  - réserve l'authentification à la dernière étape de publication, dont la
    dernière action promeut en stable/latest uniquement une prerelease issue
    de l'événement `release`, après le succès du téléversement ;
  - limite les jobs de build et de publication au repository exact
    `asphyx0r/git-starter-kit`.
- Si le workflow est absent, illisible ou non conforme, applique les mêmes
  règles d'arrêt que lorsqu'aucun template de release n'est accessible.
- Résous avec l'API GitHub l'identité exacte et l'état actif du workflow
  `Release package`. Une identité absente, désactivée, illisible ou non conforme
  arrête le workflow avant toute mutation.
- Enregistre `Release package` comme workflow de release obligatoire en plus
  des workflows communs définis par le workflow principal. Ne remplace et ne
  redéfinis aucun contrôle commun.

CRÉATION DE LA PRERELEASE

- Au point 40 du workflow principal, crée la GitHub Release pour le tag
  exact comme prerelease avec
  `--verify-tag --prerelease --latest=false`.
- Vérifie qu'elle cible le tag exact, qu'elle n'est pas un draft, qu'elle
  est encore une prerelease et que son corps correspond exactement aux
  Release Notes rendues.

CONTRÔLES DE PACKAGE APRÈS LES RUNS OBLIGATOIRES

- N'applique cette section qu'après la réussite de tous les workflows de
  release obligatoires contrôlés par le workflow principal, y compris
  `Release package`.
- Vérifie ensuite que la GitHub Release :
  - cible toujours le tag exact et conserve les Release Notes rendues ;
  - n'est ni un draft ni une prerelease ;
  - est marquée comme dernière release ;
  - contient exactement trois assets nommés
    `git-starter-kit-<tag>-with-agent-rules.zip`,
    `git-starter-kit-<tag>-upgrade-toolkit.zip` et `SHA256SUMS`.
- Télécharge ces trois assets dans un répertoire temporaire hors du working
  tree et vérifie que le SHA-256 de chacun correspond au digest publié par
  GitHub.
- Vérifie que l'asset `SHA256SUMS` contient exactement, en UTF-8 sans BOM et
  avec fins de ligne LF, octet pour octet les deux lignes attendues : empreinte
  SHA-256 minuscule, deux espaces, nom du ZIP, puis LF ; package complet
  d'abord, upgrade toolkit ensuite. Recalcule les deux empreintes depuis les
  ZIP téléchargés. Ne confonds pas cet asset avec le fichier `SHA256SUMS` à la
  racine du repository, qui inventorie les blobs de l'artefact `git-tree`.
- Vérifie le package complet :
  - il contient `AGENTS.md`, `BRANCH_RULES.md`, `CODING_RULES.md`,
    `COMMIT_RULES.md`, `DOCUMENTATION_RULES.md`, `LANGUAGE_RULES.md`,
    `RELEASE_RULES.md` et `_agent-rules-source.json` ;
  - son manifeste contient le tag et le commit exacts du starter kit,
    `requestedRef=latest`, ainsi qu'un tag SemVer et un commit résolus pour
    `agent-coding-rules` ;
  - `starter-kit-manifest.json` conserve `source`, identifie le tag exact dans
    `current` et utilise l'URL exacte de la release ;
  - `_starter-kit-files.json` utilise le schéma 3 et classe
    `starter-kit-manifest.json` avec la stratégie `starter-kit-state` ;
  - il ne contient aucun fichier réservé au repository source, tel que le
    workflow, les builders, leurs tests ou leur documentation opérateur.
- Vérifie que l'upgrade toolkit contient exactement les fichiers de cet
  inventaire JSON, en remplaçant `<tag>` par le tag publié. Cet inventaire
  est comparé au ZIP réellement construit par le test de non-régression
  `test_toolkit_matches_release_skill_inventory`.

```json
[
  "README.md",
  "starter-kit-upgrade.py",
  "process_runner.py",
  "starter_kit_upgrade/__init__.py",
  "starter_kit_upgrade/application.py",
  "starter_kit_upgrade/archive.py",
  "starter_kit_upgrade/cli.py",
  "starter_kit_upgrade/common.py",
  "starter_kit_upgrade/planning.py",
  "packages/git-starter-kit-<tag>-with-agent-rules.zip"
]
```

- Vérifie que le SHA-256 du package imbriqué est identique à celui du
  package complet publié séparément.
- Supprime uniquement le répertoire temporaire de vérification après avoir
  confirmé qu'il reste dans la racine temporaire attendue.
- Retourne au workflow principal uniquement après la réussite de tous ces
  contrôles. Aucun asset valide ni run manuel ne suffit séparément, et seul le
  workflow principal peut fixer `RELEASE_STATUS=complete`.
