Objectif : analyser puis, uniquement après validation explicite du bump,
créer les commits strictement nécessaires, s'il y en a, créer un tag
SemVer, effectuer un push atomique et, si cela est explicitement demandé,
créer une GitHub Release à partir du template `GITHUB_RELEASE_NOTES.md`,
puis appliquer les éventuels contrôles de release propres au repository.

PARAMÈTRES EXPLICITES DE LA DEMANDE COURANTE

- BUMP peut valoir : patch, minor ou major.
- BUMP est absent par défaut.
- CREATE_GITHUB_RELEASE vaut false par défaut.
- CREATE_GITHUB_RELEASE ne vaut true que si l'utilisateur le demande
  explicitement dans la demande courante.
- `GITHUB_RELEASE_NOTES.md` est optionnel tant que
  `CREATE_GITHUB_RELEASE=false`, et obligatoire lorsqu'il vaut true.
- Ne déduis jamais qu'un paramètre a été validé à partir d'une
  suggestion produite lors d'une exécution précédente.

RÈGLES GÉNÉRALES

- Travaille uniquement depuis la racine retournée par :
  `git rev-parse --show-toplevel`.
- Vérifie que cette racine correspond au repository actuellement ouvert.
- Lis et applique les instructions du repository qui gouvernent les
  opérations prévues, notamment `COMMIT_RULES.md` avant chaque commit,
  `RELEASE_RULES.md` avant le tag et les règles de documentation
  applicables avant toute mise à jour documentaire.
- Exécute toutes les commandes Git séquentiellement, une seule à la fois.
- N'exécute aucune commande Git en parallèle ou en arrière-plan.
- Ne relance automatiquement aucune commande ayant échoué et ne relance
  jamais automatiquement un workflow CI. Seules les interrogations en
  lecture seule explicitement prévues pour attendre le run CI obligatoire
  peuvent être répétées.
- Si une commande échoue ou ne termine pas normalement, arrête toute
  mutation et rapporte la commande exacte. Après un échec du run CI
  obligatoire, seules les commandes de diagnostic en lecture seule prévues
  par ce workflow restent autorisées avant l'arrêt.
- Ne lance pas `git clean`, `git reset --hard`, `git gc` ou une commande
  destructive sans validation explicite.
- Ne contourne jamais les hooks avec `--no-verify`.
- N'ouvre aucun éditeur interactif.
- N'utilise jamais `git commit -m`. Valide et transmets toujours le même
  fichier de message au hook et à `git commit`.
- Avant toute création de commit ou de tag, exécute exactement une fois :
  `git fetch origin --prune --tags`.

EXTENSION CONDITIONNELLE DU STARTER KIT

- Si le remote `origin` correspond exactement à
  `https://github.com/asphyx0r/git-starter-kit.git`, lis entièrement
  `references/git-starter-kit-release-package.txt` et applique cette
  extension aux points qu'elle remplace.
- Pour tout autre remote, n'exige aucun workflow de package, aucun asset
  de release et aucun contrôle propre à `git-starter-kit`.
- Si le remote correspond à `git-starter-kit` mais que l'extension est
  absente ou illisible, arrête-toi avant toute mutation.

PHASE 1 — ANALYSE DU BUMP

1. Identifie :
   - la racine du repository ;
   - la branche locale courante ;
   - `origin/<branche>` ;
   - l'éventuelle branche upstream ;
   - les opérations Git éventuellement en cours.

2. Arrête-toi immédiatement si :
   - HEAD est détaché ;
   - `origin/<branche>` n'existe pas ;
   - un merge, rebase, cherry-pick ou revert est en cours ;
   - des fichiers sont en conflit ;
   - le repository ne peut pas être lu correctement.

3. Vérifie que la branche locale n'est pas en retard ou divergente :
   `origin/<branche>` doit être un ancêtre de `HEAD`.

4. Recense tous les tags stables qui correspondent exactement à
   `vMAJOR.MINOR.PATCH`, présents localement ou sur `origin`, puis
   identifie le plus grand tag SemVer stable par comparaison numérique de
   MAJOR, MINOR et PATCH. Ne te base ni sur l'ordre chronologique, ni sur
   la date de création, ni sur les seuls tags accessibles depuis `HEAD`.
   Le commit déréférencé de ce plus grand tag doit être un ancêtre de
   `HEAD`. Sinon, arrête-toi sans choisir un tag inférieur comme base.

5. Applique la convention de tag suivante :
   - le préfixe `v` est obligatoire ;
   - si le repository définit une politique explicite de type de tag,
     notamment dans `RELEASE_RULES.md`, applique cette politique ;
   - considère les tags historiques d'un autre type comme des exceptions
     immuables qui ne rendent pas la politique courante ambiguë ;
   - en l'absence de politique explicite, déduis le type uniquement si
     tous les tags SemVer stables recensés utilisent le même type.
   Si des tags SemVer stables sans préfixe `v` sont présents localement ou
   sur `origin`, ou si aucune politique explicite ne permet de résoudre un
   type de tag mélangé ou ambigu, arrête-toi.

6. Si aucun tag SemVer de base ne peut être identifié avec certitude,
   arrête-toi. Ne propose pas arbitrairement `v0.1.0` ou `v1.0.0`.

7. Détermine le contenu complet de la prochaine release :
   - tous les commits du range `<plus-grand-tag>..HEAD` ;
   - les modifications locales suivies ;
   - les fichiers non suivis qui semblent destinés au commit.

8. Analyse l'effet net des changements :
   - ne te base pas uniquement sur les sujets de commit ;
   - inspecte les diffs pertinents ;
   - décompose les merge commits ;
   - prends en compte les reverts ;
   - identifie les interfaces publiques du projet ;
   - consulte la politique de versioning du repository ;
   - utilise l'historique des tags comme élément de comparaison.

9. Classe chaque changement publiable :
   - major : rupture de compatibilité publique ;
   - minor : fonctionnalité publique rétrocompatible ;
   - patch : correction ou maintenance rétrocompatible ;
   - none : aucun changement justifiant une nouvelle version.

10. Le bump recommandé est le niveau le plus élevé constaté.

PRÉCONDITION CONDITIONNELLE DU TEMPLATE DE RELEASE

- N'applique cette section que si `CREATE_GITHUB_RELEASE=true`.
- Recherche un template accessible dans cet ordre strict :
  - le fichier joint à la demande courante nommé exactement
    `GITHUB_RELEASE_NOTES.md` ;
  - à défaut d'un tel fichier joint accessible,
    `templates/GITHUB_RELEASE_NOTES.md`, résolu relativement à la
    racine du repository.
- Un template est accessible uniquement si son contenu complet peut
  être lu et s'il n'est pas vide.
- Enregistre la source exacte du template retenu pour le reste du
  workflow.
- Si l'extension conditionnelle du starter kit s'applique, exécute aussi
  ses préconditions de workflow avant de poursuivre.
- Si aucun template n'est accessible :
  - produis et affiche le rapport de bump défini au point 11 ;
  - si BUMP est absent, affiche aussi `BUMP_RECOMMANDÉ=<valeur>` et
    `TAG_RECOMMANDÉ=<tag exact>` ;
  - avertis explicitement l'utilisateur et indique les deux sources
    vérifiées ;
  - ne modifie aucun fichier, ne stage rien, ne crée aucun commit ni
    tag, ne pousse rien et ne crée aucune GitHub Release ;
  - arrête le workflow avant la phase 2.

11. Produis un rapport contenant :
    - le plus grand tag SemVer stable local ou distant ;
    - le range de commits analysé ;
    - les commits et modifications significatifs ;
    - la classification de chaque changement ;
    - le bump minimal déduit ;
    - le prochain tag exact ;
    - les éventuelles incertitudes ;
    - la justification factuelle du choix ;
    - si `CREATE_GITHUB_RELEASE=true`, la source du template retenu ou
      l'erreur bloquante qui empêche son utilisation.

12. Si plusieurs bumps restent plausibles :
    - recommande le niveau le plus conservateur, donc le plus élevé ;
    - signale explicitement l'incertitude ;
    - n'exécute aucune opération de release.

13. Si BUMP est absent :
    - affiche `BUMP_RECOMMANDÉ=<valeur>` ;
    - affiche `TAG_RECOMMANDÉ=<tag exact>` ;
    - ne modifie aucun fichier ;
    - ne stage aucun fichier ;
    - ne crée aucun commit ;
    - ne crée aucun tag ;
    - ne pousse rien ;
    - ne crée aucune GitHub Release ;
    - arrête immédiatement le workflow.

14. Si BUMP est fourni :
    - refais ou valide l'analyse ;
    - vérifie qu'il correspond au bump minimal déduit ;
    - si BUMP est inférieur, arrête-toi ;
    - si BUMP est supérieur, demande une validation explicite ;
    - ne continue automatiquement que s'il correspond exactement au
      bump déduit.

PHASE 2 — PRÉPARATION DU COMMIT

15. Recherche les fichiers `.gitkeep` parmi :
    - les fichiers suivis ;
    - les fichiers non suivis et non ignorés.
    N'analyse pas le contenu de `.git` ni les fichiers ignorés.

16. Un `.gitkeep` est inutile uniquement si son répertoire contient
    déjà un autre fichier destiné à être suivi.
    Supprime chaque `.gitkeep` inutile lorsque cet autre fichier appartient
    au périmètre attendu de la release, puis inclus explicitement sa
    suppression dans le commit concerné. En cas d'ambiguïté, conserve-le.

17. Mets à jour, uniquement si nécessaire et à partir du contenu de la
    release analysée :
    - `README.md` ;
    - `TODO.md`, s'il existe.
    Ne mets pas encore à jour `CHANGELOG.md` : prépare-le uniquement après
    la finalisation des commits publiables.

18. Examine l'état du working tree autant de fois que nécessaire avec
    `git --no-optional-locks status --porcelain=v1`, notamment
    immédiatement avant chaque commit, immédiatement avant le tag et après
    le push. Utilise aussi `git status --short --branch` lorsqu'il faut
    contrôler la branche et son upstream.

19. Vérifie les fichiers staged, modifiés et non suivis. Exclus les secrets,
    identifiants, fichiers locaux, données privées, artefacts temporaires et
    fichiers non désirés. Répartis les changements publiables en commits
    distincts par intention lorsqu'un seul message exact ne peut pas les
    représenter. Ne mélange jamais une préparation pure de `CHANGELOG.md`
    avec un changement fonctionnel, comportemental ou documentaire.

20. Il peut y avoir zéro, un ou plusieurs commits. Ne crée jamais de commit
    vide. Stage un seul commit candidat à la fois, uniquement à partir d'une
    liste explicite de fichiers attendus. N'utilise pas `git add .` ni
    `git add -A`. Si l'historique contient déjà les changements publiables,
    que le working tree ne nécessite aucun commit et que le changelog est
    valide, aucun nouveau commit n'est nécessaire.

21. Pour chaque commit candidat, vérifie le contenu staged avec :
    - `git diff --cached --name-status`
    - `git diff --cached --check`
    - `git ls-files -u`

22. Immédiatement avant chaque commit candidat, vérifie l'état du
    repository, exécute `git fsck --full` et lance les plus petits contrôles
    de projet applicables aux fichiers staged. Répète `git fsck --full`
    immédiatement avant le tag, même si aucun nouveau commit n'est
    nécessaire.

23. Avant chaque commit, analyse le contenu staged avec
    `betterleaks git --staged --redact --no-banner`. Si Betterleaks est
    indisponible ou ne peut pas valider le contenu, avertis l'utilisateur et
    utilise `gitleaks protect --staged --redact --no-banner`. Si aucun des
    deux outils ne peut effectuer la validation, avertis l'utilisateur,
    inspecte intégralement chaque fichier concerné et effectue une recherche
    conservatrice de secrets. Un secret confirmé ou une incertitude non
    résolue bloque le commit.

24. Vérifie que chaque commit du range de release est lisible et accessible
    depuis `HEAD`. Arrête-toi si :
    - un secret ou fichier non désiré est staged ;
    - un conflit existe ;
    - le diff contient une erreur ;
    - le contrôle d'intégrité échoue ;
    - un contrôle de projet applicable échoue sans dérogation explicite ;
    - `origin/<branche>` n'est plus un ancêtre de `HEAD` ;
    - ni le range actuel ni les changements attendus ne contiennent de
      changement publiable.
    L'absence de contenu staged n'est pas un motif d'arrêt à elle seule si
    aucun nouveau commit n'est nécessaire selon le point 20.

PHASE 3 — COMMIT ET TAG

25. Pour chaque commit candidat, inspecte `.gitmessage` s'il existe et la
    configuration résolue avec `commitlint --print-config json` lorsque
    commitlint est disponible. Déduis le message exact du diff staged et des
    règles du repository.

26. Le titre du commit doit :
    - être rédigé en anglais ;
    - contenir au maximum 50 caractères ;
    - respecter le format Conventional Commits et les règles résolues ;
    - décrire succinctement le changement principal.

27. Le corps du commit doit :
    - être rédigé en anglais ;
    - contenir des lignes de 72 caractères maximum ;
    - décrire les modifications apportées ;
    - expliquer succinctement leur raison.

28. Commitlint est obligatoire. Vérifie d'abord que `.githooks/commit-msg` et
    `commitlint.config.cjs` sont suivis et lisibles, puis valide le message
    exact avec `commitlint --edit <fichier-temporaire>`. Le fichier temporaire
    doit être hors du working tree, encodé en UTF-8 sans BOM et contenir le
    message complet définitif. Immédiatement après cette validation et avant
    le commit, exige que le hook et la configuration soient restés inchangés.
    Sans modifier ni reconstruire le message, crée le commit depuis la racine
    avec exactement :

    ```text
    git -c core.hooksPath=.githooks commit \
      --file=<même-fichier-temporaire> \
      --cleanup=verbatim
    ```

    N'utilise ni `-m`, ni `--no-verify`. Après le succès, compare le message
    enregistré par Git au fichier validé et exige une identité exacte hors
    fins de ligne finales normales. Supprime uniquement ce fichier temporaire
    après cette vérification. Si commitlint est indisponible, s'il échoue, ou
    si un hook, la création du commit ou la comparaison échoue, arrête
    immédiatement le workflow. Répète les points 18 à 28 pour chaque autre
    commit publiable nécessaire.

29. Une fois les commits publiables finalisés, vérifie ou mets à jour la
    section exacte du prochain tag dans `CHANGELOG.md` à partir de
    l'historique Git. Si le fichier doit changer, crée un commit distinct de
    préparation du changelog en répétant tous les contrôles applicables des
    points 18 à 28. Si la section est déjà exacte, ne crée aucun commit de
    changelog. Vérifie ensuite que :
    - le working tree est propre ;
    - aucun fichier attendu n'a été omis ;
    - `origin/<branche>` est toujours un ancêtre de `HEAD` ;
    - le range contient au moins un commit publiable autre qu'un éventuel
      commit de préparation du changelog.

30. Calcule le tag exact, toujours préfixé par `v`, à partir du
    plus grand tag SemVer stable et de BUMP :
    - patch : incrémente PATCH ;
    - minor : incrémente MINOR et remet PATCH à zéro ;
    - major : incrémente MAJOR et remet MINOR et PATCH à zéro.

31. Utilise le type de tag résolu au point 5. Lorsqu'une politique
    explicite l'impose, ne reproduis pas le type d'un tag historique
    exceptionnel.

32. Relis les tags présents sur `origin`, recalcule le plus grand tag
    SemVer stable et vérifie que le tag calculé n'existe ni localement ni
    sur `origin`. En cas d'évolution distante incompatible ou de collision,
    arrête-toi. N'incrémente pas automatiquement une seconde fois.

PRÉPARATION CONDITIONNELLE DES RELEASE NOTES

- N'applique cette section que si `CREATE_GITHUB_RELEASE=true`.
- Après la création des éventuels commits et avant la création du tag,
  génère les Release Notes dans un fichier temporaire situé hors du
  working tree.
- Utilise exclusivement le template retenu pendant la phase 1 et ne
  modifie jamais le fichier source.
- Préserve la structure, l'ordre, les titres, les colonnes et les
  textes fixes du template.
- Remplace chaque occurrence de `vX.Y.Z` par le tag exact calculé.
- Remplace `{RELEASE-SUMMARY-NOTES}` par une synthèse factuelle de la
  release.
- Dans `Highlights`, produis un nombre quelconque de puces supérieur
  ou égal à un. Répète ou supprime les lignes de puces du template
  selon les changements réels, sans appliquer de limite arbitraire.
- Dans le tableau `Changes`, produis exactement une ligne par
  changement publiable identifié pendant l'analyse. Répète ou
  supprime les lignes du template selon les besoins.
- Chaque ligne de `Changes` contient les références Git
  correspondantes, une date au format ISO `YYYY-MM-DD`, une
  description factuelle et les auteurs Git dédupliqués.
- Ne laisse aucun placeholder non résolu. N'invente aucune section,
  colonne ou structure absente du template.
- Si les Release Notes ne peuvent pas être générées et validées à
  partir du template, avertis explicitement l'utilisateur et
  arrête-toi avant de créer le tag ou d'effectuer le push.
  N'utilise aucune structure de remplacement ni aucune génération
  automatique de notes.

PRÉVALIDATION DISTANTE OBLIGATOIRE

- Applique cette section avant toute création de tag, avec ou sans GitHub
  Release demandée.
- Exige que `.github/workflows/repository-audit.yml` soit suivi, lisible,
  nommé exactement `Repository audit`, déclenché par `push` et qu'il publie
  un job agrégateur nommé exactement `Repository audit` pour les pushes non
  manuels. Ce job doit réussir uniquement si tous ses jobs enfants réussissent.
- Exige que `tools/verify-repository-audit-runs.py` soit suivi, lisible et que
  son aide et sa version puissent être exécutées. Utilise uniquement cet outil
  suivi pour sélectionner et attendre les runs d'audit obligatoires.
- Résous l'identifiant exact de ce workflow avec l'API GitHub. Si le workflow,
  son identité ou son contrat ne peut pas être vérifié, arrête-toi avant le
  tag et avant tout push.
- Inspecte la protection de `origin/<branche>`. Lorsque GitHub permet les
  checks requis pour ce repository, exige le check `Repository audit` fourni
  par GitHub Actions, l'application aux administrateurs et l'absence de bypass.
  Une protection absente, relâchée ou impossible à inspecter arrête le workflow
  avant le tag et avant tout push. Si cette fonctionnalité GitHub n'est pas
  disponible pour le repository, rapporte la limitation et demande une
  validation utilisateur explicite avant de continuer sans cette couche.
- Enregistre le SHA distant exact de `origin/<branche>`, vérifie de nouveau que
  le tag calculé est absent localement et sur `origin`, puis construis le nom
  unique `codex/release-preflight-<tag>-<sha-court>`. Arrête-toi si ce ref
  existe déjà sur `origin` ; ne le remplace et ne le force jamais.
- Pousse uniquement `HEAD` sur ce ref avec
  `git push origin HEAD:refs/heads/<branche-preflight>`. Ce push de
  prévalidation est distinct du push atomique final. Enregistre immédiatement
  avant le push un horodatage UTC `YYYY-MM-DDTHH:MM:SSZ`.
- Recherche le run unique qui respecte simultanément :
  - l'identifiant exact du workflow `Repository audit` ;
  - `event=push` ;
  - `headBranch=<branche-preflight>` ;
  - `headSha=<SHA exact de HEAD>`.
- Attends ce run jusqu'à son état terminal. Exige `status=completed` et
  `conclusion=success`. Aucun run manuel, planifié, portant un autre ref ou un
  autre SHA ne peut le remplacer. Un run absent, multiple, annulé, expiré,
  ignoré, neutre ou en échec arrête le workflow avant le tag.
- Effectue cette attente avec :

  ```text
  python tools/verify-repository-audit-runs.py \
    --repository <owner/repository> \
    --workflow-id <id> \
    --sha <SHA exact de HEAD> \
    --ref <branche-preflight> \
    --created-after <horodatage-UTC>
  ```
- Après le succès, relis `origin/<branche>` sans le modifier et exige qu'il
  corresponde encore au SHA distant enregistré. Relis aussi les tags distants
  et exige que le tag calculé soit toujours absent. Toute évolution ou
  ambiguïté arrête le workflow ; ne rebase, ne merge et ne recalcule rien
  automatiquement.
- Conserve le ref de prévalidation jusqu'à la réussite du push final et des
  runs finaux. Si le workflow s'arrête avant cela, rapporte ce ref exact et ne
  le supprime pas automatiquement.

33. Immédiatement avant de créer le tag, exécute
    exactement une fois `git fetch origin --prune --tags`, puis
    `git status --short --branch`, vérifie que le working tree est propre,
    qu'aucune opération Git n'est en cours, que `CHANGELOG.md` est exact et
    que le SHA cible est celui attendu, puis exécute `git fsck --full`.
    Crée le tag uniquement après la réussite de toutes ces vérifications.

PHASE 4 — PUSH FINAL ET VALIDATION

34. Pousse la branche et le tag ensemble dans un unique push final :
    `git push --atomic origin <branche> <tag>`
    Enregistre immédiatement avant ce push un nouvel horodatage UTC au format
    `YYYY-MM-DDTHH:MM:SSZ`.

35. Si le push échoue :
    - ne réessaie pas ;
    - ne force aucun push ;
    - ne déplace aucun tag ;
    - rapporte précisément l'état du commit et du tag local ;
    - vérifie si possible si le remote a été modifié ;
    - arrête le workflow.

36. Après un push réussi, exécute exactement une fois :
    `git fetch origin --prune --tags`

37. Compare :
    - `git rev-parse HEAD`
    - `git rev-parse origin/<branche>`
    - `git rev-parse <tag>^{}`

38. Les trois identifiants doivent être strictement identiques.

39. Vérifie finalement que :
    - le working tree est propre ;
    - la branche locale et la branche distante sont synchronisées ;
    - le tag local et le tag distant correspondent ;
    - le repository ne comporte aucune erreur détectée.

CONTRÔLE CI FINAL OBLIGATOIRE

- Applique cette section après le push atomique et avant toute GitHub Release.
- Réutilise l'identifiant de workflow `Repository audit` résolu pendant la
  prévalidation et le SHA exact vérifié au point 38.
- Le run de tag est toujours attendu. Le run de `origin/<branche>` est aussi
  attendu lorsque le SHA distant enregistré avant la prévalidation différait
  de `HEAD`.
- Pour chaque ref attendu, recherche le run unique avec simultanément :
  - l'identifiant exact du workflow `Repository audit` ;
  - `event=push` ;
  - `headBranch` égal au tag ou à la branche attendue ;
  - `headSha` égal au SHA cible exact.
- Utilise `tools/verify-repository-audit-runs.py` avec le repository,
  l'identifiant de workflow, le SHA, le nouvel horodatage UTC et un argument
  `--ref` répété pour chaque ref attendu.
- Attends tous les runs attendus jusqu'à leur état terminal. Un run
  `workflow_dispatch`, planifié, portant seulement le même SHA ou provenant
  d'un autre workflow ne peut jamais remplacer un run attendu.
- Exige pour chaque run `status=completed` et `conclusion=success`. Si un seul
  run est absent, multiple, annulé, expiré, ignoré, neutre ou en échec, conserve
  le ref de prévalidation, fixe `REPOSITORY_AUDIT_STATUS=incomplete`, collecte
  les métadonnées et logs utiles en lecture seule et arrête le workflow sans
  créer de GitHub Release. Un autre run vert du même SHA ne compense jamais cet
  échec.
- Après le succès exact de tous les runs, supprime uniquement le ref de
  prévalidation créé par cette exécution avec
  `git push origin --delete <branche-preflight>`, puis vérifie son absence sur
  `origin`. Une suppression impossible ou ambiguë arrête les mutations et est
  rapportée.
- Fixe `REPOSITORY_AUDIT_STATUS=complete` uniquement après ces contrôles et ce
  nettoyage.

40. Une GitHub Release ne peut être créée que si :
    - CREATE_GITHUB_RELEASE=true a été fourni explicitement ;
    - toutes les vérifications finales ont réussi ;
    - `REPOSITORY_AUDIT_STATUS=complete` ;
    - les Release Notes ont été générées et validées à partir du
      template retenu.
    Lorsque ces conditions sont remplies :
    - si l'extension conditionnelle du starter kit s'applique, utilise
      sa procédure de création et de validation ;
    - sinon, crée la GitHub Release stable pour le tag exact avec
      `--verify-tag --latest` et sans asset ;
    - fournis explicitement comme corps le contenu rendu du template ;
    - n'utilise jamais de notes générées automatiquement ni de
      structure de remplacement ;
    - si l'extension s'applique, exécute ses vérifications immédiates ;
    - sinon, vérifie qu'elle cible le tag exact, qu'elle n'est ni un draft
      ni une prerelease, qu'elle est marquée comme dernière release, que
      son corps correspond aux Release Notes rendues et qu'elle ne
      contient aucun asset.
    Sinon, ne crée et ne publie aucune GitHub Release.

CONTRÔLE CONDITIONNEL DE LA GITHUB RELEASE

- Si l'extension conditionnelle du starter kit s'applique, exécute son
  contrôle CI obligatoire et fixe `RELEASE_STATUS` selon son résultat.
- Sinon, fixe `RELEASE_STATUS=complete` uniquement après avoir vérifié la
  release stable, son corps exact, son statut latest et l'absence d'asset.
